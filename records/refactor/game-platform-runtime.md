### 实现

- 完整快照与窗口共用 Timeline 物化路径。按既有索引取精确消息/变体键，SQL 每批最多 256 个键，FS 最多 16 个在途读取；保留 journal 未提交覆盖层、缺失依赖、跨账号拒绝、顺序和全部变体。Native 仓库写入/Save 导入已接纳的不可变元数据不在普通读取时递归重新准入，仍核对身份、分支祖先、选择引用和 HEAD。
- 缓存宿主拥有且深冻结的记录值/回执的规范 JSON、字节数及 SHA256，最多 4,096 项、32 MiB UTF-16 文本权重，单项不超过 8 MiB。可变对象不按引用缓存。旧规范字节和持久化摘要不变；已存在的状态对象不再解码并复制一次仅为丢弃结果。容量统计复用相同不可变子树大小。
- 已提交行动回执共享不可变内容，候选与发布仍持有独立可写容器；普通仓库读取仍可修改自己的副本。保留其他 namespace 的可写候选，不能因为 base 被冻结就返回无法写入的 Subject/世界容器。
- 现有 ID 索引扩展字段相等和 ID/字段并集查询，每个视图最多八个字段索引。候选相同值的视图共享懒构建索引，写入复制受影响 bucket，成员删除和认知重绑失效。首次构建只扫描并选择一次，不再次计量已访问的匹配结果；热查询按实际命中/lookup 计量。
- 验证期间发现摘要模块与记录复制形成初始化循环，已将纯不可变身份和状态复制分离。还修正了首次索引构建重复选择/计费，以及候选共享范围过宽会冻结可写 namespace 的问题；相关入口和隔离测试重测通过。

### 规模与边界验证

- 同一份 20,001 条消息/变体的 SQLite 持久化样本：旧主线冷读取 542.65 ms、40,002 个时间线 SQL 查询；新实现 419.66 ms、314 个查询，完整快照逐项一致。此样本为历史规模夹具，不能代替上述真实游戏证据。100 条窗口仍有序，单条存储调用为 11（另有批量读取）。
- 实际 FS 与 SQLite 检查批量乱序键、重复键、缺失键、600 键分批、跨账号拒绝、事务覆盖层/回滚、历史祖先/身份/缺失依赖，以及公开可变回执与内部共享回执隔离，均通过。
- 受影响候选/状态验证：真实 FS 的 50k 记录跨 revision 身份复用、外部修改隔离、新非法值拒绝；文件修改/删除/损坏失效和 journal 故障恢复；CPU 计算期间同账号读取、精确重放及过期 CAS 拒绝，均通过。所有修改 JS 的 ESLint 和 diff whitespace 检查通过。PostgreSQL/MySQL 更新相同批量接口，但没有运行对应数据库服务。

完整冷加载仍必须读取并生成所请求的全部内容，改变后的 namespace 仍需处理完整规范字节以保持现有 SHA256 身份；本轮消除的是逐条请求、重复准入/复制、重复子树序列化及重复集合筛选，没有谎报 O(1) 冷加载或增量 Merkle 格式。当前自然场景端到端收益约 8%，明显小于局部收益，剩余游戏计算、沙箱传输和规则准入成本仍应以具体负载剖析，不能继续仅凭这些局部数字推断大型游戏帧率。
