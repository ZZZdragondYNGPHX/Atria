### 实现

- 完整快照与窗口共用 Timeline 物化路径。按既有索引取精确消息/变体键，SQL 每批最多 256 个键，FS 最多 16 个在途读取；保留 journal 未提交覆盖层、缺失依赖、跨账号拒绝、顺序和全部变体。Native 仓库写入/Save 导入已接纳的不可变元数据不在普通读取时递归重新准入，仍核对身份、分支祖先、选择引用和 HEAD。
- 缓存宿主拥有且深冻结的记录值/回执的规范 JSON、字节数及 SHA256，最多 4,096 项、32 MiB UTF-16 文本权重，单项不超过 8 MiB。可变对象不按引用缓存。旧规范字节和持久化摘要不变；已存在的状态对象不再解码并复制一次仅为丢弃结果。容量统计复用相同不可变子树大小。
- 已提交行动回执共享不可变内容，候选与发布仍持有独立可写容器；普通仓库读取仍可修改自己的副本。保留其他 namespace 的可写候选，不能因为 base 被冻结就返回无法写入的 Subject/世界容器。
- 现有 ID 索引扩展字段相等和 ID/字段并集查询，每个视图最多八个字段索引。候选相同值的视图共享懒构建索引，写入复制受影响 bucket，成员删除和认知重绑失效。首次构建只扫描并选择一次，不再次计量已访问的匹配结果；热查询按实际命中/lookup 计量。
- 验证期间发现摘要模块与记录复制形成初始化循环，已将纯不可变身份和状态复制分离。还修正了首次索引构建重复选择/计费，以及候选共享范围过宽会冻结可写 namespace 的问题；相关入口和隔离测试重测通过。

### 定位与实现

- 初始三天剖析：122 次 compute、244 次 invariant。guest 游戏计算约 378 ms；宿主 JSON 准入约 483 ms、privateReads 约 322 ms。函数计时存在包含关系，不能相加为总耗时。首批准入/借用修改后的第二轮剖析进一步发现发布累计约 2,819 ms，其中 journal commit 1,447 ms，首次主线程编译约 477 ms；这组发布数字不是未修改起点的精确分项基线。
- 严格 JSON 准入在一次遍历内为每个拥有的冻结子树记录精确 UTF-8 JSON 字节数、节点数、深度和最长字符串；后续读取/类型验证/计费复用身份，较小限额照常拒绝。沙箱返回 JSON 由宿主解析后原地验证冻结，移除紧接着的深复制。外部对象仍按描述符、原型、密集数组和键约束接纳，浅冻结不能绕过验证。
- 同一事务的前后 invariant 重新收集当前授权 reads；完整输入（包括 guest 能观察的对象键顺序）相同才复用成功判定，保留两份原有逻辑 evidence。任何变化仍执行规则。真实三天物理 invariant 调用 244 → 122，四会话 976 → 488；没有跨事务缓存判定，也没有省略变化后的不变量。
- 运行时首次 JS/TS 转译进入既有计算子进程池。宿主收集有界静态依赖，固定源字节后异步编译；构建与运行仍是同一 compiler、相同 artifact/hash。复用原队列、取消和进程 deadline。修复异步编译过程中可写 source Map 被修改时，缓存错误绑定到新字节的风险。每次执行仍创建新 guest context，模块全局不延续。
- 状态持久化和 CAS 的内部只读比较借用已有 immutable resource 接口，不为读取 integrity 复制整份文档。FS 的独立 namespace 准备采用四路有界并发；SQL 保持串行。失败后等待所有并行准备结束再退出事务。
- FS redo 改为 `ATRJ2`：索引和 payload 一起校验摘要，存放每份目标资源的精确编码字节；四路异步 zlib 压缩后，日志与安装复用同一份结果，避免双重 JSON 序列化/压缩。目标文件仍为原 JSON/`ATRZ1`，恢复兼容旧日志；发布顺序、文件 sync、commit-last 和删除日志屏障保留。正常 rename 后不再执行必定找不到临时文件的删除调用。
- 引擎首次访问及任意事务失败后恢复 journal；同 root 的引擎实例共享失败失效标记。成功普通读取不再反复检查 journal 文件。最终三天诊断 recover 703 次事务中仅实际运行 2 次；仍不支持多个服务器进程同时写同一 FS root。

## P9：Native WAL 耐久发布与首次冷编译（2026-10-25）

起点 `main@bf7e7e92`；产品实现 `9f0ac008`。本轮针对逐事务多文件耐久发布和首次编译退化，未增大游戏执行预算、改变人口/资产或删除一致性屏障。

### 实施

- FS 模式的 Native 记录改存每账号 `atria-native/resources.sqlite`，直接复用现有 `native_resources` 表、键编码、索引、批读和 CAS；每个逻辑事务独立 `BEGIN IMMEDIATE` / WAL `synchronous=FULL` / COMMIT 后 ACK。原 Session/Revision/receipt/RunControl 发布权威不变，外部 Blob 仍先耐久写入再发布引用。Legacy chat/文件没有被包装成虚假的跨文件 SQL 原子事务。
- 首次访问先恢复已提交旧 JSON/ATRZ1/ATRJ2 日志，再逐文件流式导入。记录和账号/版本 marker 在同一 SQL 事务内提交；完成后数据库是唯一读取权威。旧资源移至 `pre-wal-resources` 作为不参与读取的恢复副本，删除不会复活；维护扫描游标重建，避免沿用旧文件排序。旧 journal writer/overlay 已移除，只保留恢复解码；SQL 损坏 JSON 不再静默当作记录不存在。
- 在线备份使用 SQLite backup API，和事务/checkpoint 共用账号队列；ZIP/恢复点不复制活动 DB/WAL/SHM 或旧恢复副本。临时恢复源重绑定数据库账号；恢复前关闭连接，资源计量排除数据库物理字节的重复计入；Host 生命周期也跟踪新备份/checkpoint 操作。
- 世界 JS/TS 转译使用固定 `esbuild@0.28.2`（MIT）的原生服务，在原计算子进程池内执行，避免每个冷子进程再加载 TypeScript 全编译器。宿主现有源码 AST 和生成产物检查保留，UI Controller 编译保持原样。构建与运行时使用同一转译器和 hash；首次可达源字节在异步前固定。
- 并发冷启动按完全相同的源字节共享编译和产物校验。单个调用取消不伤害其他调用，最后一个调用取消仍终止池中作业。保持原背压、deadline、fresh guest context 和不可信代码进程隔离。编译器变化导致新世界执行证据的 artifact hash 变化，旧回执没有被改写。

研究使用 [SQLite WAL](https://www.sqlite.org/wal.html)、[online backup](https://www.sqlite.org/backup.html)、[esbuild transform](https://esbuild.github.io/api/#transform) 和 [固定版本许可](https://github.com/evanw/esbuild/blob/v0.28.2/LICENSE.md)。本机 better-sqlite3 12.10.0 的 SQLite 为 3.53.1，已包含官方说明的 WAL-reset 修复；没有引入日志同步降级或运行时自动退回较弱存储。

## P10：冷包与四并发宿主延迟（2026-10-25）

起点 `main@9f0ac008`；产品实现 `8a5db095`。本轮同时测吞吐、事件循环延迟、真实操作响应与关闭后的冷重载。没有扩大计算、内存、集合扫描或事务批处理预算。

### 根因与实施

- 并发冷打开在等待 Blob 租约前保存了旧 cache 状态，准入 Promise 却在取得租约后才登记。后续等待者取得租约时，前一准入已经完成并被移除，因而再次解密/展开同一包。现在先按 owner/content/stamp 加入共享准入，再取得租约；四调用实测只取得一次 payload 租约，失败可重试，文件变化仍拒绝。
- 冷包原本逐条等待 ZIP 读/解压完成。元数据与声明大小闭合后，四路使用现有 filesystem/zlib worker 读取独立条目；缓冲配额和 spool 范围在等待前按归档顺序预留，仍按同一生成器顺序验证 CRC、inventory digest、manifest 与前端资源。错误时等正在读取的条目结束再关闭 backing，不增加 32 MiB 驻留配额。
- 未压缩的非驻留条目校验后直接借用已认证 plaintext ZIP 范围，避免再写一次；压缩条目仍落解压文件。引用持有 backing，GC 清理改异步；显式释放和进程退出仍清理。借用可能保留整份 plaintext ZIP，混合包可能同时保留 ZIP 与解压 backing，并非无磁盘成本。
- 私有读投影从逐记录/逐字段 split 与重复拷贝路径改为前缀树；完整且键顺序相同的选择可复用封闭记录。内部持久状态写入复制可变封套、共享既有不可变 payload，消除整棵 structuredClone；公共返回值隔离和规范摘要不变。
- 更快的 WAL 发布使四个会话的 CPU 工作更集中；仅 await 已完成的存储 Promise 不能让事件循环服务其它任务。实验中共享一个让出 Promise 仍同时唤醒四条微任务链。现在在动作开始和发布前使用 FIFO 合作调度，每个轮次恢复一个等待者，4 ms 为宿主合作粒度；SQL 事务内没有 yield，Session lock、CAS、COMMIT 后 ACK 全部保留。
- 操作聚合原先只检查“已用时间 < 250 ms”，会在临近窗口末尾再启动一个完整原子事务。现在用上一逻辑步的实测时间判断下一步是否可容纳；仍是 250 ms / 8 步、仍返回已有 continuation。单个冷/复杂事务仍可超过窗口，不宣称硬实时保证。

## P11 — 单会话 JSON 数据流水线与冷编译（2026-10-26）

产品 `4e2af884`，基线 `8a5db095`。继续使用原始 106,778,956-byte 斗破发行包、同一自然起点，未改游戏、执行预算、分片配置或耐久条件。测试、profile 和私有状态夹具仅留本地。

### 原因与实现

九日诊断的累计宿主发布约 4.82 s，沙箱 compute 往返约 5.31 s；worker 的实际游戏计算约 1.86 s，模块初始化约 0.91 s，输入处理约 0.87 s。时间有包含关系，不相加为关键路径。CPU 样本暴露 JSON inspect 约 967 ms、规范序列化约 636 ms、SQL parseRow 约 662 ms，以及逐次输出 schema 编译；这些是诊断运行，不与下面无 profiler 的正式结果混算。

- 私有投影直接构造拥有复杂度与精确字节元数据的不可变 JSON；效果准入保留安全副本。copy-on-write reducer 保留已准入叶节点，后续重叠路径赋值仍复制沿途容器。移除“准入 → 深复制 → 再准入”的重复工作。
- 公共 action 在等待锁之前捕获外部输入，内部 continuation 复用其所有权。公开 transaction catalogue 直接投影已有冻结声明，保留 schema 身份；不可变 computation output schema 只编译一次。未知对象与较小预算仍由原准入边界拒绝。
- canonical SHA256 直接消费不可变 payload 的 UTF-8 buffer 和可变封套片段，避免整 namespace 字符串拼平后重新编码。规范字节与 SHA 不变，32 MiB 总保留权重同时计算 UTF-16 文本和 UTF-8 buffer，4096 项与单项上限未扩大。
- 内部 SQL 摘要/CAS 读取捕获原 row 文本，首次访问 doc 才解析；公共读取仍立即解析。解码状态保留 depth/replayBytes，避免为了几个元数据字段重解整个 delta 文档。原快照、缓存失效、CAS、逐事务 WAL/FULL 不变。
- 宿主用轻量 module lexer 收集 JS 依赖；完整源码/生成代码检查与转译进入原有计算池。JS 用 Acorn，TS 按需加载 TypeScript，避免每个首次 JS 编译启动完整 TS 编译器。静态精确路径、源字节捕获、源/产物规则、取消、队列背压和 fresh context 保留。
- 前端绑定与游戏任务复用既有精确源/Data/contract 的声明编译权威，减少首次动作重复编译。新增直接依赖 `es-module-lexer@1.7.0`、`acorn@8.16.0` 均来自现有锁文件，已核对本地源码接口与 MIT 许可。扫描器只收集依赖，不替代源码准入；TS 依赖捕获仍使用语法解析。

直接对象 IPC 的九日实验约 15.54 s，比 JSON 文本路径更慢，撤回。递归合并整棵返回树、逐子树规范缓存和重新构造排序对象的实验无稳定收益或更慢，也撤回。最终实现没有预热后计时，也没有调大缓存或工作预算。
