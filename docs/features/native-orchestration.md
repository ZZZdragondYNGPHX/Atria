# Native Agent Plans and Runs

Open **Agents → Plans** to create a graph. Edit nodes and typed ports in the canvas or list and Inspector. Choose the exact Session, Project task or chat under Revisions to bind that revision. A Binding does not start work or grant execution permissions.

Open **Agents → Runs** to select a source and follow its Runs. Chat starts require an explicit preflight and paid start. Project trusted commits require a current reviewed task, an exact published commit Plan, preparation, a separate trusted Review window and explicit dispatch.

The Timeline and Graph show the same Host projection. Costs distinguish known usage, unknown usage and reserved limits. Cancel does not undo work already sent or refund unknown fees. Closing a page does not cancel the Host operation.

Desktop uses a canvas and Inspector; mobile offers an equivalent node/edge list and sheet. Memory keeps its own scoped read and maintenance surface. External tools cannot register executable authority through a Browser capability registry.

RP, Game and Project main graphs and delegated child graphs implement combinations of published Agent, Planner, Review and Judge tasks: DAG dependencies, bounded return edges, dynamically added owned Agents, and safe local Review redo of pure-model Planner work. A saved or published graph alone does not prove that every combination can execute.

Independent-Actor collaboration in main RP graphs has existing FS, SQLite and SQL execution evidence. Delegated child Actor contexts use owned Actor pins, authorized Information and recipient-specific Result visibility. Frozen Fanout scopes support Judge-to-successor-Agent work across the three domains.

Published advisory child Plans can delegate further through the same Host, resource permits and budget tree, including from an Agent inside a frozen branch. Parallel delegators retain separate parent-attempt state, child allocations and Return bindings. Review can redo a completed pure Fanout/Join group when the entire group is downstream of the reviewed task and all costs are settled. New attempts and barriers retain the old results and fees. A completed pure advisory delegation can also be reviewed and redone through a new child Run and a fresh allocation from the original budget; the old Return remains tied to its original attempt. Pending-task cancellation and explicit blocked outcomes are also connected.

The sole Narrator output boundary and Project’s formal tools and human Review remain in force. Before Join, a branch Review can redo its own nonterminal predecessors and then feed their new results to the still-unstarted frozen terminal; unrelated branches retain their work. A branch Planner can request bounded rework along published return edges within its own scope, before the frozen terminal starts. Repeated work gets new Attempts and retains its original costs; unstarted members keep their reserved identities, and sibling branches keep their work. A frozen scope cannot change topology, replace its frozen terminal, or attach a completed sibling to a new Join. Nested Fanout scopes and cross-scope replan remain restricted. Unknown costs remain unknown.

The retired Browser execution modes, preset settings and checkpoint protocol have no execution or migration path. Historical files outside the active protocol remain inert; current domain data, receipts and unknown costs are retained.

Plans can be copied from a saved draft or an exact published revision. Derive
records an exact published source and creates an independent draft containing
that graph and its pins. It does not create runtime graph inheritance. Archive
and restore organize the library without changing existing Bindings or Runs.
Only never-published drafts can be deleted; published history remains readable.
All lifecycle mutations use the original command envelope and compare the draft
version/hash. An unknown result must be retried with the same command ID/body.

A model node can pin a Prompt Program independently of its Runtime Route using
`policy.promptPinId`. The Program pin uses `port:"model"` and a Library, Project
or Package exact resource reference. The original owner and current execution
source still control which scoped resources are available.
