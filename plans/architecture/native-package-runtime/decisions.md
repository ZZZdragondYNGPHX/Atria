# 冻结决策与设计授权

本文件只拥有跨模块方向。具体表达、字段和算法属于对应模块；更改此处边界需说明影响并与用户讨论。

## D01 — Package 与 Atria 的责任

Package 定义“游戏怎么玩”；Atria 定义“这些规则怎样被可信地执行并写入正式历史”。战斗、交易、任务、掉落、NPC 决策等业务算法可以属于 Package。

平台合法性由 Atria 定义：Capability、身份、Session / Revision、并发、Schema、读写与资源边界、提交权限。游戏领域合法性由 Package 固定规则定义。两层合法性均由 Atria Authority 执行和强制。

## D02 — 原生能力目标与生态边界

吸收外部项目体现的需求和设计思想，形成 Atria 能力模型。旧插件 API、数据格式、角色卡和脚本兼容、迁移方案、插件内置或复刻均不在本任务范围。

EJS、全局函数库、iframe 脚本、window API、特殊文本指令与 decorator、旧变量作用域和存储方式均不构成预设设计。具体技术只能依据 Atria 自身需求选择。

## D03 — 调用者提出领域操作

Experience Script、UI、AI 和自动化通过获准 Command / Intent 表达操作语义与参数，不能提交任意 StatePatch 作为正式写授权。

固定规则执行形成候选结果，领域和平台检查通过后由 Authority 提交，产生正式 Revision 与处理 Receipt。平台检查覆盖执行前、执行中和提交前。

## D04 — 固定资源与双重版本依据

规则与检查代码必须来自当前运行绑定的固定 Package 版本及其正式资源闭包。调用者不能临时提供 validator、替换规则或用自备校验结果证明自身合法。

Package 规则版本和 State Revision 分别标识规则依据与状态依据；资源引用和操作输入需要保持真实身份。

## D05 — 脚本用途与执行边界

Experience Script 负责交互、生命周期、自动化、Task 编排和提出操作。Domain Logic 由 Authority 调用，负责游戏计算与候选结果，没有正式提交权。

Prompt、Knowledge 内容派生、输出处理及 UI Controller 的可编程能力也按执行用途授予输入和结果边界。共享执行技术或便利函数不合并权限；VM 数量、进程边界和模块格式尚未冻结。

## D06 — 声明式契约与复杂算法

Atria 必须理解并强制 Command、输入 Schema、Capability、规则绑定、Precondition、Invariant 和 Effect 边界。契约声明检查点、范围和正式依赖，复杂算法及谓词允许由受控 Package Logic 实现。

不要求所有游戏规则转写为 JSON DSL。脚本可以使用私有数据和局部可变工作模型，正式候选与提交仍由平台控制。

## D07 — Domain Logic 的 I/O 边界

Domain Logic 默认不直接调用模型或外部 I/O。计算使用已捕获且依据明确的输入；模型参与通过显式 Task / Generation 产生结果，再由固定领域规则消费。

结构化输出只证明数据形状，不能证明领域合法性或授予写权。Package 可以规定模型判断参与玩法，但须消费获准生产者的真实结果。

## D08 — State 的归属、生命周期与读取

数据有明确归属与生命周期，正式写入由所属 Authority 提交。Script、Prompt、Knowledge、Task 和 UI 按消费用途获得读取权限，并保留正式来源与版本依据。

能读取某份数据不等于能将它用于任意模型上下文或对任意受众展示。Scope 名称、查询表达和视图结构由技术设计确定。

## D09 — Task 产物消费

Task 产物保留真实生产身份、输入、资源和状态依据。Package 固定契约定义允许用途、有效条件和复用规则，由 Atria 在消费时强制。

允许明确契约下的跨 Revision 复用。领域操作仍绑定正式应用基准并重新执行当前规则；旧 Effects 不能直接套用，编辑后的同形 JSON 不能冒充原始正式产物。

## D10 — Prompt / Knowledge 与正式变化

动态 Prompt 与 Knowledge 内容派生属于基于获准输入的只读上下文计算。模型工作由显式阶段执行，正式变化由相应 Authority 提交。

动态展开后的实际内容进入组合与最终请求预算。Knowledge 的持久选择状态随相应结果正式采用提交；预览、编译和重新渲染保持正式 State 只读。具体采用边界由技术设计确定。

## D11 — Processing 与消息

Processing 按阶段和用途执行有界转换，可以产生候选文本、结构化数据或操作建议。正式消息与领域状态分别由对应 Authority 校验并采用。

正式消息版本是历史来源。模型上下文与 UI 呈现从获准来源派生，不因派生自动回写其他表示。沿用 MessageProjection 的正文一致性与无执行权限数据边界。

消息编辑是显式正式操作；流式片段与正式采用产物具有不同身份。可执行逻辑来自正式资源，模型文本不因模板、代码或组件标记获得执行权限。

## D12 — 原生编排与作者工具

Lifecycle 承载 Package 的受控运行编排；Atria 负责触发、调度、恢复和正式提交关系。事务内规则仍由 Authority 执行，事件驱动编排提出后续工作。

Studio / Runtime Diagnostics 是正式能力，应帮助作者定义、验证并理解原生执行，沿用实际资源、授权、快照和提交证据。具体事件与追踪格式尚未冻结。

## D13 — 工作方式

用户只把控能力范围、职责边界和关键取舍。Agent 自行推导技术契约、事件、字段、Schema、API、执行适配和验证，不逐项要求用户确认。

S0 轮次只发布正式企划与换设备交接，没有编写产品实现或创建开发分支。CP1–CP3 的历史交付组映射见 index；当前执行规则由 Governance 管理。
