## v0.16 新增后端目标

首要工作是补齐无需玩家接任务的自主世界循环：NPC 能谋生和补充必需物资，接纳工作、旅行、采集、返程交付与照护有完整执行过程；首批家庭/商铺/组织围绕有限资源和可支配资金产生需求，再由成员或外部合作者执行。其上加入持续目标、主动社会行为与长期地区反馈。顺序及完成依据统一归制作稿 W0–W5，不在这里另建第二份阶段表。

V8–V10覆盖无参与世界循环、持续目标/主动社会与多尺度成本；V11/V12新增连续因果/机会性改策和全角色个人图谱。受影响的动态身份、完整恢复、人口和真实模型样本仍沿用V1–V7。先用规则与既有存档证明真实运行，再为需要模型的复杂决策验证质量；不让每个内部生活事件调用模型。长期常规计划的执行与真正等待生成的决策需分别表达。

V13增加NPC自主成长和后台冲突/物品损耗。先补角色能力/功法与物品状态，再由NPC按本人所知选择修炼或战斗策略，规则读取双方真实能力和资源结算；战后补给、养伤、维修与报复/避让都进入世界。后续完整玩家战斗单独实施，本轮不新建该战斗控制/界面或以其完成作为验收前提。统一能力、物品与结果语义供未来复用，不把本版后台公式强加给未来玩家机制。

图谱基础、感知相遇、事件与动机的持久来源进入W0/W1；W3贯通多目的活动、潜在仇怨及机会性插队，W4连接跨人物后果。新增跟随、调查、抽象拘束/逃脱/释放、威胁传话、协商与求援等语义，以具体可结算需求选择最小动作集合；不把两段用户示例分别写成固定脚本，也不让模型临时发明未经声明的效果。所有受影响角色包括家人、路人及玩家都有有效行动条件，玩家选择仍由本人控制。

## 功能完整路径与当前开工点

每项功能先按 [implementation-readiness](implementation-readiness.md) 核对承载与缺口，再在同一实施路径补齐下列环节。它们是执行者逐项落实和自查的要求，不是新增审批阶段；已有可用承载直接复用，不机械重做。

| 环节 | 后端实施要求 |
| --- | --- |
| 状态与 schema | 明确事实归属、主体/实例身份、生命周期、来源和恢复范围；拟定字段与现有 C2 实际字段分开。不能仅在计划中写出功能名或在旁白中声称有此状态 |
| 合法写入、条件与事件 | 声明谁能在何种前置条件下接纳和修改状态，实际 effect 如何落账，失败或中断保留什么；产生可追溯事件，时间与资源变化进入相同权威路径 |
| 动作有效性与 AI 选择 | 状态参与移动、交互、物品使用、活动及冲突的有效性判断；NPC 从有效候选中按本人所知和目标选择，失效后能解释、等待或改策。规则约束同样适用于玩家，玩家选择仍由本人控制 |
| 按视角读取与失败原因 | 交付真实可消费的读取路径，覆盖本人状态、合法可见角色详情、可用动作及可解释失败原因；区分客观事实与观察/本人所知，不因详情或拒绝原因泄露他人隐私、秘密位置或未知伤势。明确未知、不可见、不可用和读取失败的差异 |
| 保存与分支 | 持久状态、引用关系、待执行活动和已提交效果可完整恢复；读档后条件、角色详情及 NPC 选择一致，旧分支或迟到模型结果不能写入新分支 |
| 代表性验证 | 用实际规则和宿主读口证明正常、失败/中断、条件变化及保存/恢复路径；需要模型的选择另用真实模型验证。仅有文案、局部计算、循环无异常或接口字段名不算功能完成，验证资产按既有规则仅本地保留 |

以下状态必须有实际承载并影响规则，不得只作叙事描述：身体部位的骨折、缺失和功能约束及其恢复；物品实例、归属、数量/次数/充能与适用损耗；拘束、释放、逃脱等约束状态；社会关系图谱、个人知识与来源；NPC 活动进度、占用和中断，以及组织生产的投入、产出、资金和义务。详细语义沿用相应领域模块，不在此预造实现字段。

发现某个叙事结果依赖尚不存在的状态、条件、动作或读取能力时，先补相应承载、effect 与验证，再让结果可被规则接纳。缺少正式 UI 时保留功能需求并交付后端状态和最小读取验证；不能删掉想法，也不能先写成已经发生但无法查询、约束后续行动或保存的结果。

当前从制作稿 W0 开工：核对 be.2 真实 schema、合法写入和 effect 的现有依赖，列出当前身体/物品/约束、事件来源/个人图谱及活动/组织资源承载中的实际缺口；按后续动作所需先补状态，再接 W1 执行与读口。实施中只更新已查明的依赖、接口和结果，不继续以无目的文档追加替代代码落地。具体参数用实现与样本校准，规则承载缺口不转为等待用户逐项确认。

## 必须保持的权威与验证

- World/Domain 保存位置、资源、家庭、人口和已发生事实；复用已有 Actor/Subject、Information/Cognition/Memory、Clock/Simulation、Revision/SavePoint，避免平行身份、关系或存档系统。
- 动态 Subject 评价目标与确定性 Bridge 已在 be.2 对应框架补齐；新增目标/委托/组织/历史数据要沿用这些已存在路径并验证授权与恢复。历史 manifest 限制不能当成当前仍未修复的阻碍。
- 文本、按钮、后台 NPC 活动使用同一规则；模型只提出或表达，接纳后才修改状态。个人所知、传闻、原著记忆与本局事实分开。
- 思考、编辑、菜单与离线暂停；行动及已提交部分耗时不能由动画或现实等待改变。长时推进处理竞争和到期事件，不跳过中间资源因果。
- 存档恢复覆盖整个本局世界及人口名额、个人信息和任务；真实迟到结果不得写入恢复后的新分支。外部记忆若存在必须证明隔离，不能假定自动恢复。
- 后端负责受当前范围影响的V1/V2/V3/V4/V6/V7及新增V8–V13，V5覆盖路径/目标变化/重复提交等规则；完整玩家战斗按D33后续单独实施，最终视觉/焦点/浏览器体验沿旧分工。
- 测试/诊断用入口和资产仅本地保留，不提交测试代码、fixture、日志或截图；Record 保存环境、样本说明和结论。由执行者自查，不启动独立审查。

## 供前端接手的具体交付

1. 正式包源、可复现构建/导入说明、版本化结果与必要框架修补的实际 HEAD；若生成 `.atria`，说明它是后端验证构建，不能宣称最终视觉完成。
2. [共用契约](frontend-contract.md) 中 F01–F12 的真实字段、读取与写入落点、命令/任务参数、权限与错误；补齐本轮功能的按视角角色详情、条件/失败原因与最小读取验证。标注已实现、条件可用、未实现及实测状态，不把候选语义编成 C2 已存在的新字段。
3. 典型输入输出的文字说明或最小内联示例：新局、接近移动、NPC 对话、交易、争夺、家庭、人口新增、保存与恢复；实际验证 fixture 不提交。
4. 模型配置要求、实际质量/调用/等待和长时负载结果；接口是否取消、何时已提交、能否重试需依据现有能力写明。
5. 集成尚需完成的组件、正式美术、Canvas/Controller 接线与玩家查看/操作/反馈/恢复的端到端验证清单。BE 不替用户决定后续接手者，不因设计仍在迭代而把已完成后端工作搁置。

逐项区分“BE完成”和“集成完成”：前者要求真实状态、合法 effect、动作条件/AI 使用、视角读口、保存分支和代表性验证均已交付；后者另需实际玩家界面接线及操作闭环。没有最终界面可交付 BE 完成，但不能标为玩家功能已集成；规则存在但合法角色详情读不到或失败原因无法消费时，也不能标为 BE 完成。

当前拆分不要求后端制作最终视觉，也不删减家庭和长期演化。be.2 是已交付基线；后续按 W0–W5 深化，不能将最小可运行骨架、循环次数或无异常退出代替世界自主性。新增能力进入真实构建后再修订 C2 或后续契约版本。
