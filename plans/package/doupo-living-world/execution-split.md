# 前后端任务拆分与并行安排

状态：v0.19，be.5/C4已有默认世界运行后端与代表性证据；W5成本/聚合继续深化。BE/FE及后续集成分工不变，实际状态和来源归[同一Record](../../../records/package/doupo-living-world.md)。

## 两条并行工作与后续接线

| 工作 | 负责的结果 | 当前执行边界 | 入口 |
| --- | --- | --- | --- |
| BE 后端开发 | 可结算、可恢复的游戏世界、内容与玩家视角数据，必要的 Atria 框架修补 | 新对话连续实施首批规则和内容；界面仅保留验证所需的最小操作入口 | [后端任务](backend-task.md) |
| FE 前端设计迭代 | 可交互 HTML、全功能表现文档、视觉与组件指导 | 与 BE 并行使用离线示例数据迭代；不改实际世界规则或接管后端 | [前端 AI 委托](frontend-ai-brief.md) |
| 后续前端集成 | 把选定方案接到真实 Atria Package，完成表现、美术与整包验收 | 后端完成后，由用户决定交给当前 AI 或其他 AI；目前不自动指定执行者 | [共用契约](frontend-contract.md)与前端三项产物 |

这里的“后端”包括包内权威规则、内容数据、模型任务和已有 Host 能力的接线，并非另建一个独立服务。正式作品继续采用 Atria 原生前端能力；外部 HTML 是设计与交互参考，不直接等同 `.aui` 成品。

详细玩法只有[制作稿](production-plan.md)及领域模块一份权威。双方共用数据与状态语义归 [frontend-contract.md](frontend-contract.md)，不在两份委托中各造接口。

功能完成路径归 [implementation-readiness.md](implementation-readiness.md)，身体细则归 [character-condition.md](character-condition.md)。BE交付合法读口和最小读取验证，FE设计覆盖所需信息，集成者接成玩家能打开、理解和操作的界面。三者分别记录实际进展；“接口已提供”不等于“伤势详情可玩”，正式美术也不成为BE补齐规则承载的前提。完整玩家战斗及其新控制/交锋界面按D33后续独立实施，角色身体详情不因此省略。

## 文件与工作空间边界

拟采用以下游戏目录；实际作者源格式由 BE 核对原生构建契约后确定，不为分工另造目录框架：

```text
package:doupo-living-world/
├─ README.md              # 构建、导入与实际入口
├─ source/                # 正式 Package 作者源；具体布局由真实构建方式确定
├─ design-reference/      # FE 的 HTML、功能表现、设计指导和自制设计素材
└─ releases/              # 版本化 .atria，历史成品保留
```

- BE 管理正式包源、构建与发布；FE 设计仅管理 `design-reference/`。双方不修改对方所有的文件。
- 设计 HTML 可内含必要的离线演示数据；测试 fixture、脚本、运行日志和截图仅临时本地保留，遵循 [Governance §12](../../../README.md#12-execution-adapters)。设计资料不是测试资产，也不放入 docs 分支。
- BE 可以搭建最小验证入口；若构建必须包含前端声明，由 BE 保留最小占位，不覆盖设计稿、不展开正式视觉制作。正式前端文件的所有权在选定集成者后再转交。
- Plan/Record 由后端开发对话维护；外部 FE 通过其功能表现文档中的“接口需求与设计提案”交付意见，不并行改写 decisions、共用契约或 Record。
- 需要产品修补时，在独立语义源码任务工作树执行；`main` 不合入 `package`。不改 Atria 全产品前端审计任务的代码或文档。
- 同机并行时使用各自隔离工作树，记录所属分支与 HEAD；禁止两个对话同时操作同一个工作树的索引/提交。FE 三项产物由其分支提交后，仅迁入所属游戏目录；BE 不把新建分支名或尚不存在的工作树记成已建立。
- 只有得到用户提供的文件编辑权限时，外部 AI 才写本地目录；否则交付三个完整文件，由本地执行者导入。不得覆盖其它任务改动。

## 从前端审计中提取的协作方法

参考 [外部设计 AI 委托](../../architecture/atria-frontend-audit/external-design-ai-brief.md)、[实施输入](../../architecture/atria-frontend-audit/claude-code-frontend-prompt.md)与[设计指导](../../architecture/atria-frontend-audit/design-proposal/atria-frontend-guidelines.md)：

1. 用少量精细 HTML 场景表达视觉方向，用功能表现文档覆盖全部首批能力，用设计指导维持组件与素材一致性。
2. 功能以稳定 ID 映射入口、操作、状态和恢复；HTML 未画到的能力仍保留，原型演示不升级为已实现功能。
3. 视觉、真实数据接线和后端权威分开交付；复用现有宿主能力，记录实际可用与待验证项。
4. 保留目标、等待、失败输入、保存冲突和恢复等操作语义；产品内部事务与诊断信息按需放开发工具。

审计目录描述整个 Atria 平台。本任务只借用其资料组织和协作方法；不继承全平台 189 项清单、Dock/活动灵动岛或 Atrium 配色，也不把平台作者审查流程引入本任务的执行步骤。游戏画面按 [presentation.md](presentation.md) 展开。

## 并行顺序与完成边界

1. BE从be.5/C4与Record的真实结果接续W5成本/聚合及剩余行为覆盖；修正实际断点，避免重做已验证的默认切片。同时FE按C4区分已实现接口和候选需求制作原型。
2. BE 发现真正接口形状后，在共用契约补上来源文件/绑定/样例、可用能力及未完成项，更新同一 Record。保留语义意图，字段按真实能力确定；FE 根据更新调整输入输出，布局迭代无需等待后端全部完成。
3. BE 完成首批全部游戏规则与内容、模型验证和负载验证后，交付可复现包源/构建结果、实际能力矩阵、接口资料与已知限制。此时报告“后端完成”，不报告“整款游戏发布完成”。
4. FE 可持续和用户迭代三项资料。后端完成并不自动冻结最新设计；用户选择集成执行者后，该执行者读取真实契约和用户选定的设计版本，再完成正式原生界面、美术及 V5/整包验收。

制作阶段无需逐段请求继续，也不引入独立审查。本轮按用户要求重新对照方案与代码承载，只更新设计与实施依赖；后续实现沿既有授权连续推进，不重新等待拆分或参数审批。
