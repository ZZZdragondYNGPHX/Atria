## 一项功能的完整路径

| 环节 | 实现必须回答的问题 | 不足以作为完成证据的情况 |
| --- | --- | --- |
| 状态与身份 | 什么持久事实发生变化，主体/物品/来源引用何处，schema如何表达 | 仅有故事文案、字段名或一个通用标签 |
| 合法写入 | 哪个动作、事件或活动能创建/修改/结束状态，有何前提与代价 | 模型随意给补丁，UI自行改库存或角色状态 |
| 机械后果 | 如何改变可执行能力、效果、时间、资源、风险和后续事件 | 状态写上去了，人物仍照旧做所有事 |
| 决策与所知 | 哪些人能知道哪些变化，AI怎样把它用于选择与改策 | 后台状态对全体公开，或AI完全不读取状态 |
| 投影与操作 | 玩家/模型能读到什么，人物详情如何解释限制，能做什么来应对 | 后端仅私有字段，无实际读口；UI只有漂亮示意图 |
| 保存与历史 | 未完成过程、来源、身体/物品和认知怎样随分支恢复 | 只恢复最终数值，读档后丢限制、重复结算或串入未来 |
| 对应验证 | 用什么代表性过程证明上述连接，失败和重试怎样处理 | 只验证schema通过、流程不报错或模型会说这段话 |

同一状态在多个系统产生影响时，统一查询其实际能力/效果与原因；避免旅行、战斗、工作、修炼各写互相矛盾的一套限制。派生能力可以按需计算或缓存，但原始身体/物品/活动事实只保留一个权威。

## 以用户伤势例子贯穿实现

“A使B重伤并损坏手脚”需要先明确发生的是骨折、暂时失能还是肢体缺失；具体区别见身体模块。不同后果可以共存，但不能只写入injury=90再由不同地方任意解释。

实现切片至少贯通：

1. 角色初始化具有可表达的身体与伤记录；NPC冲突的合法结果创建具体伤势及来源，而非旁白先宣布。
2. 人物能力统一推导，当前装备/动作/旅行/工作/修炼重检。例如需要相关肢体能力的动作不可用，活动中已发生部分保留。
3. B及实际观察者获得各自能知道的结果。B可据此求助/休养/改策，A只按自己观察到的情况决定后续，不读取完整私有诊断。
4. 正式读取投影能提供本人伤处/功能限制/治疗状态、相关不可行动原因，NPC只显示已观察或获知的表现；前端把它落实到可打开的人物/伤势详情。
5. 治疗产生有条件的实际变化，永久缺失不被通用减injury或普通回血自动修复；解除限制或仍然受限都要有原因。
6. 途中/治疗中保存，继续变化，再恢复并推进，身体、能力、装备、活动、所知和详情回到同一历史分支。

后端可先用真实读取和本地最小验证入口证明状态/能力/投影路径；角色详情正式接线由既有FE/集成分工完成。没有画完正式界面不妨碍后端实现，但该玩家功能在接线前只能标“后端已实现、界面待集成”，不能宣称整项可玩。

## 构建与宿主预算也是承载条件

新增能力需要同步核对以下真实作者入口，不另造通用服务来回避现有契约：

- state初始值、新角色默认值/准入输出、Domain记录schema和允许命令。
- read grants字段/集合/数量、invariant所需的最小授权输入、computation输出schema与有界effects。
- Information sources/views及主体scope、NPC判断使用的字段、玩家与叙事的合法投影。
- screen/detail读取schema、Bridge绑定/输入/错误、实际前端消费者、保存/恢复及历史引用。

be.2代码中的8人物/8信息/4评价输出、有界集合和公开观察预算均影响扩展；a9已有CPU/输入/schema预算。不能把所有新状态无限嵌入每个人和每次公开screen，也不能先提高全局限额掩盖结构问题。

先用有代表性的身体、器物和个人关系数据验证闭合schema、包构建/安装、真实授权读取/写入与恢复。必要时用有界记录集合、按需详情和稀疏引用减少冗余；具体选择以编译/真实宿主样本为依据，不在本文件宣布某一结构已经通过。

涉及容量的记录要分别统计活跃状态、历史来源、投影、序列化和扫描成本；接口只返回某人的少量记录并不证明没有全域扫描。命中限制后说明具体瓶颈和修正结果，不换Domain、删除活跃证据或复用死者ID来隐藏增长。

## 状态、表达与生成的联系

能力目录与接纳路径定义规则可以产生哪些实际效果。NPC规划和自然语言解析只能提出可执行候选；前提不足时返回可理解的拒绝或缺口，不创建一条已经成功的文本结果。

关键事实如伤处/缺失、物品转移、控制关系和生死应有基于规则结果的稳定表达；模型只使用获准事实展开人物表达。未经实现或未被本次规则结果产生的“断肢”“装备损毁”“家属被扣留”等不能作为系统事实发布。

模型生成错误时修正或重试表达、采用已有事实的受控表达，不按错误文字反向补写世界，也不重做已提交扣费或攻击。自由文本一致性与规则正确性分别验证，不能声称仅靠提示词永不误述。

## 实施顺序与完成状态

W0先形成少量关键状态/作用/读取的实际实现；W1接合法动作与能力限制，再让W2–W4的经济、主动社会和长链使用它们。每完成一段即更新真实契约与Record，避免先铺满所有剧情然后发现底层无法表达。详细阶段仍只有 [制作稿](production-plan.md#实施顺序与完成依据) 一份权威。

实现涉及身体、装备、控制、关系或生产时，同步该行为的状态、动作、视角和保存路径；不将全部领域列为每次改动的必测集合。检查范围只按 [Governance §12.2](../../../README.md#122-minimal-validation-and-runtime-checks)。

| 实际进展 | 可以报告的完成程度 |
| --- | --- |
| 只有文档/概念字段 | 设计完成，待实现 |
| 有代码但未通过真实声明/构建/运行 | 实现中，不宣称可用 |
| 状态/规则/读口及恢复有实际证据 | 后端对应能力已实现，注明样本与边界 |
| 已有真实界面读取/操作/限制反馈 | 该玩家功能已接线，注明尚欠的玩法或视觉 |
| 目标场景含失败/中断/恢复贯通 | 对应范围完成，保留实际容量与未覆盖部分 |

并非每个对象都需要独立页面：人物详情、行囊、活动/关系详情等可复用入口。但每个影响玩家理解和决策的状态，都要有合法可读且可理解的表达。完整玩家战斗按D33仍在后续范围；身体和世界后果不因此只留文字。

### 高频重复任务的容量与调度承载

源码调查所见：世界`promises`总上限64，开放约定最多16，玩家投影最近32条，意图投影最多四条开放约定且仍受裁剪；当前未见终态约定回收路径。任务机制不能直接把所有任务追加进该数组，也不能把婚约混入统一清理。实施需按任务机制定义保留必要终态摘要、结算凭据、任务链依赖及尚未解决事项，再区分热状态、历史查询与可重建索引；应补未付、待归还或责任未定等事项及其工作/投入/退出依据不能随已撤/已放弃任务归档消失，已计贡献、已归还和已付依据仍需防止重复履行。不得通过删除活动任务、证据或支付依据伪装长期运行通过。验证必须跨过终态累计超过64及多次重复接约的实际过程，不能只看同时开放数量。

长期合作按有界期次和必要触发依据维护，不能预先无限展开未来订单；多单并行复用共享资源/工时与相关事实变化索引，不为每次界面展示全量扫描合同或重建路线。测量跨多期后终态/欠款增长、同时参与单数、共享资源重检、行动前冲突估计的读取/计算量与积压；暂停或终止不删除尚未清算期次。具体窗口与并行容量需据实际宿主成本确定，本节不宣称通用新调度器或无限并行已可用。

当前计算采用有界读取和输出：人口身体分批33/32/32，认知按需最多8人，单次身体变化最多6、认知最多4、信息最多6、评价最多2；Domain与公开screen也有各自字节/记录限制。任务实例、全文、阶段条件和世界扫描不得全部塞进每人认知或每次screen。按相关对象、事实变化与期限检查任务，记录每次读取/更新量、公开数据体积、扫描成本及积压推进次数；实际结构以编译和宿主样本校准，不能先普遍提高限额。

任务所需期限、取消、中断、同刻事件和长时推进接入既有共同世界时钟；持续跟踪任务不意味着每分钟调用模型。world.2沿用有界被动批次，保留每次逻辑Revision，以有界物理提交及原差分/无损文件压缩减少成本；96人跨月/全年Native容量与年度规则对照已有Record证据，但全年仍约100分钟。W5的区域/依赖唤醒、扩展规模、完整多年宿主与长期历史增长仍未闭合，这些是已知能力边界，不是每次任务改动都要重跑的长时样本；只在本次实际修改调度、容量或历史增长路径时检查相关成本。

### 事务、批次与容量

既有实现每次提交的身体写入最多6、心智4、因果2、关系评价2、个人信息6，按需心智读取最多8；world记录与计算输出各有65,536字节边界，公开screen和意图另有预算。证据入口为 `package:doupo-living-world/tools/build.mjs:99`、`package:doupo-living-world/source/rules/engine.js` 的输出检查及 `package:doupo-living-world/source/rules/records.js:31`。这些是当前每次提交的承载限制，不是已确认“每场最多6人”，也不证明任意人数已可支持。

拟先区分完整场次状态、当前决策读取、一次逻辑行动/回合结果和Native提交批次，按相关参与者、实际目标与所知加载。必要的分批不能改变战斗规则或偷偷删掉群体效果；所有批次必须共用遭遇、快照版本、稳定行动标识和随机依据。

群体/AOE需要逻辑原子的部分，应先形成完整候选结果与待提交清单，再验证一次合法原子发布或具有等价隔离保证的可恢复提交机制。不能仅在UI隐藏部分身体写入，就声称世界没有观察到半轮结果；后台生活、消息、任务和NPC决策也不得读到矛盾的半成品。

若确需跨多个commit，拟持久化结算阶段、目标清单、批次游标、已应用证据、待发布结果、随机游标和相关世界事件。只有完整结算边界才发布可交互战斗投影和后续事件；失败、超时与重新载入从最后合法阶段继续，不能重新抽取或重复扣费。此机制是否由现有Native事务完整承载必须实测，当前不宣称已有跨事务原子隔离。

Bridge的 `revision/idempotencyKey/epoch` 与战斗内部行动标识各承担不同职责：前者防重试和旧分支写入，后者防同一逻辑行动跨批次重复应用。不能仅更新请求key规避重复，也不能用旧key把新回合误判成重放；旧读档后的迟到意图/批次必须被隔离。

同伴请求的拟定工程路径还需关联战前分工、每轮短令和执行期间的自主决定，避免把三者混作玩家可反复改写的同一个即时命令。已确认的指挥方式不冻结这些阶段的字段/接口；决定快照记录接纳时可用的本人信息、真实请求版本和资格/资源依据，重检与后备细则只引用战斗模块。

普通短令不占主要行动、复杂沟通需代价已确认；短令数量、可达范围、送达条件、沟通精度、具体代价与意图分享程度仍未冻结。实现时按最终领域规则读取传达来源、身体/环境能力与预算，不默认无限短令或免费复杂沟通；新请求/版本/回复增长计入既有预算，不能每次编辑草稿都调用模型、建立事实或唤醒全部同伴。

世界时钟推进、挂起活动和已到期事件需明确同一结算边界及继续顺序。暂缓处理不等于删掉事件或停止其它地区生活；不可在战斗批次之间又让同一人物完成原工作、重复旅行或另参加第二场冲突。原有catchup机制仍需结合新遭遇占用验证。

容量工作先测参与者、群体目标、状态数、热遭遇、历史增长、公开投影与每批effects/CPU/读取字节。优先复用查询、削减重复数据和有依据的热/历史分层；不默认提高预算。若原子性、时间粒度或容量遇到可重复的真实瓶颈，再提出独立产品修补及针对性验证，不直接删掉已确认玩法或凭空承诺新核心能力。

现有 `package:doupo-living-world/source/rules/state.js:21` 的 `hp/qi=100` 初始化及 `package:doupo-living-world/source/rules/engine.js:219` 的休息重置是旧有限切片，不是新容量/质量/恢复机制。新派生资源结构、计量与恢复结算须贯通schema、输出、effects、公开视角和保存；不能把改显示或临时提高Native预算当作已实现。

已确认首批范围先使境界映射、可执行效果、种族身体/感知、实际生成/来源与合法投影闭合，再测主体、能力/物资、个体认知、公开分页和历史增长对既有预算的影响。物种数量不决定个体容量；种族与既有角色/生态如何计数、初始化/后续生成名额及工程结构仍拟定，不因“魔兽池”名称默认突破人口、读取、写入或记录上限。

### 拟定实施顺序

以下组织新对话收到正式开工指令后的实施；本规划对话不执行，也不引入独立审查或逐阶段批准。执行边界沿 [D125](decisions.md#d125--完整方案确认与实施细节授权)。

| 顺序 | 产出 | 依赖与完成依据 |
| --- | --- | --- |
| S0 规则与承载细化 | 把D89–D124映射到现有schema、身份、空间、时钟和公开路径；按已定内容、投放、首领、关闭、队伍与分配建立清单，纳入16模板、具体奖励库存、防护配置与D122–D124操作规则 | 明确同一事实权威和当前容量，严格提前离境／同刻崩解优先；已定清单均有承载与未来验证对应，同时参战／区域活跃预算另行承载 |

| S3 遭遇和内容 | 四座按已定安排逐座贯通；落实6类精英、四位核心首领各三招两阶段与多种应对、10物种、机关替代解法、资源与协商分配、具体奖励清单、试炼通过／真实交付，以及防护白名单与操作 | 四座逐一有不同目标、真实操作、资源来源、结果和世界接续；D111及D122–D124可操作，新增材料有真实用途，已定有限库存与防护容量／消耗有持久来源；不以原型演示替代已定完整覆盖 |
| S4 正式操作与验证 | 完整公开接口、前端／文字、自然流程、失败／重放／恢复和目标规模容量验证 | 下方矩阵按变更范围执行；必要界面自检由执行者完成，失败修复后相关复测 |

S1–S3各自同时贯通数据、合法写入和最小公开操作，不能等到S4才发现机制无法操作。D89–D124包含的内容、参数和规则均为已定覆盖；16模板、已列具体奖励数量、防护配置及机关／通过／交付／防护操作均纳入未来实施验证，不能因参数尚待调校而缩减清单。按D125，剩余具体字段、坐标、价格、技能数值、贡献判据和工程参数由执行者沿已定目标编制、校准与验证，不新增逐项用户确认或独立审查要求；涉及实质范围或体验变化时再讨论。整体交付以确定范围全部完成及对应证据为准，不把阶段完成当作自动停止点。

### 拟定承载与验证方向

建议先确定材料种类／批次／角色认识和制作成果的唯一事实，再贯通获取、转移、生产、使用与保存；复用现有Authority、世界时钟、内容池和完整恢复。玩家、NPC、组织和考核调用同一制作规则，各自保留操作、计划与资格职责。新接口确认后只更新原frontend-contract。

后续定向验证应覆盖：同种不同批次转移不丢性质；公开投影和模型输入不泄露未识别内容；经典方中庸目标与自创功效可实际使用；改名不改变效果；保存方子不生成材料或成品；环境／器具差异可解释；实际耗材、取消、异常与重复请求不复制产物；制作过程、知识和随机依据完整恢复。D132已纳入量产，还需检查缺料、租期和器具损耗下的停止与接续，具体异常处理见v0.75领域推荐。

D131要求公开信息经必要性与角色所知筛选，研究进度不能成为原始隐藏属性的全量导出开关。后续检查涵盖材料详情、选料预览、排序、交易、失败提示和模型上下文：必要数量与已知效果清晰，提示可据实际事实解释，未识别风险与内部权重不被间接泄露。具体字段和提示规则仍按领域设计落定。

D132新增真实小游戏、手工次数与批量资格承载，D133明确按每张实际配方分别累计，D134明确只计成功手工结算，累计五次才解锁。需关联配方身份，不能以副职或丹药品类总次数解锁；实际成功判定参数、配方规范化和继承按v0.75领域推荐及整体确认落实。一次成功制作只增加一次，不按产出件数计数；废丹、失败、取消或未完成不增加次数，也不清零已有累计成功。重复回执、重开界面、配方改名不应重复增加；次数、已投入材料、过程与结算依据纳入同一恢复边界。

建议前端处理输入与表现，由现有Authority核验本次工单、材料、过程和结果，避免直接接受任意“高分／品质”来生成成品。具体过程提交粒度按选定小游戏和宿主预算设计，不将每帧视觉变化写入世界。输入、暂停、取消、失焦、读档与迟到结果需要有明确语义；现实小游戏计时和世界时钟分开。短快简单的节奏沿D135，D136确定按住／松开控火与一次收丹、约10–20秒体验目标，精确时长与参数待校准。

未来定向验证包括累计第4／5次成功的解锁边界、成功之间穿插失败不增不清零、一次多颗成品只计一次、同类丹药不同实际配方的进度隔离、取消／未完成不计数、配方身份、良好操作与废丹、环境器具的实际作用、批量一般品质而非复制历史精品、重复提交与恢复，以及实际浏览器中的输入和过程反馈。当前没有实现小游戏或执行上述验证，不以拟定界面或阶段名称代替真实玩法与美术。

D135的难度承载需区分炼丹副职能力与配方制作要求，不能直接复用战斗`rank`当炼丹等级，也不能仅以丹药绝对等级给所有角色同难度。未来对照同方不同炼丹能力、同人不同制作要求、较大越级差距及环境／器具变化，检查难度方向和条件校验；不通过重复步骤或延长时长制造高级难度。D136的按住／松开输入需处理松手丢失、触屏取消、失焦和恢复，不让低帧率或网络回执时延改变有效操作评分；收丹只接受本次工单有效阶段的一次结算，重复点击不重复产出或累计成功。具体映射与验证样本待实施，当前未实现或验证。

v0.75已集中给出内容、作用目录、容量起点与新局推荐，详细玩法和数量只归两份领域文档；技术结构与实际预算在实施中核实。同规则保存恢复沿D18，本次新局／不迁移仍属于待整体确认的推荐。当前仅方案更新与文档检查，没有执行新增规则测试、构建、Native、浏览器、真实模型或存档操作，也未新增实现Record或HANDOFF。

候选内部字段可用`recipeKey`、`lotId`、`jobId`等表达职责，但不在规划阶段冻结完整schema或新公共API。实际接口只进入原frontend-contract；模型仍提出合法意图、解释已提交结果，不能凭自然语言创建效果、补原料或提高品质。

### 需要一起改造的现有路径

1. `person-data.js`的`qty/add/transferItem`及其调用方：显式区分按种类查询、按批次选用与唯一物转移。交易、赠礼、任务交料、尸体取物、遗产、秘境存物和组织生产都要保护批次与来源，不能只改制作页。
2. `engine.js`的炼药／用药、`life.js`的个人／药铺生产、`quest-activities.js`的考核：共用工单和产物判定，保留各自时间、操作者、权限、评价与资格。
3. `equipment.js`和战斗装备读取：从固定三类规格扩展为结构模板加实际工艺属性的实例，原槽位与佩戴条件集中维护。新器物提供真实作用，耐久与维修不另建第二套。
4. `condition.js`、成长和战斗效果：接入清单药物／符箓所需的有限效果种类，包括恢复、防护、气息、短时能力和专门成长限制。清单中的新增能力缺口必须补齐，不能用“已有状态”假装已经生效。
5. `wildlife.js`、`dungeons.js`、`exploration-state.js`和生态函数：从对应来源生成批次，尸体部位有一次性可取额度，资源节点有成熟与耗尽状态；不重写既有秘境截止／归属。
6. `projection.js`、`tools/frontend.mjs`与意图投影：新增必要的已知材料、配方进度、工单、工具／场地报价与结果视图。原始隐藏参数不进入静态`ITEMS`、公开库存、模型上下文或错误信息。
7. 前端沿`Game.aui/state/view/pack/main`现有结构接入场景制作对象、配方册和三个小游戏；通过共享工作区和分页控制节点预算，不直接叠加巨大永久面板。技术限制用实际编译器核对。

### 工单与小游戏提交

开工交易核验并占用材料、工具和时段，生成固定工单与种子。前端只处理实时输入与反馈；内部轨迹由同一规则定义派生，提交记录的输入变化与有效操作时间，不接受随意指定品质的字段。

推荐验证器按固定逻辑时步重放输入摘要，再由世界规则结算；表现帧率不决定积分。连续按住／松开可压缩成事件，不每帧写世界；锻打与符路记录有界事件，鼠标、键盘、触摸统一为逻辑输入。具体宿主读取／写入规模以实测选择，不构建平行服务器或放宽Native限制。

暂停和显式保存持久化操作进度，失焦／指针取消解除按住；恢复保持种子与工单。提交中保留原`revision/key`核对，迟到结果不能落到另一炉或另一存档分支。批量与手工共用最后结算阶段，成品、消耗和成功计数原子写入。

世界工时通过已有调度推进：先有投入与过程，后有完成或真实中断，不能先发成品再推进可能被取消的耗时。场地变更、角色失能、工具状态和到期事项按相应时点处理。首次实现用自然流程检验暂停／继续，而不只在纯函数里比较分数。

### 容量与性能

推荐容量起点见领域规则，实际schema、名册、账本、投影与资源预算按运行宿主核实。玩家批次和配方列表分页，NPC保持实际需求量；状态记录不能为每一个品质数字生成目录条目。

对库存、工单与场地用稳定索引和依赖更新；成熟节点按下次到期或查询唤醒，批量按炉／有界完成批次推进，NPC不逐帧游戏模拟。复用已有分段账本和无变化记录复用；不能通过合并有差异批次、删除重要来源或历史伪装优化。

美术预算分别检查作者原图、运行交付图、归档总量和实际加载峰值，包文件大小不直接等同媒体运行预算。图标按实际使用尺寸编码，复用稳定资源与必要缓存；源码确认不支持的懒加载或图集不得写成已具备能力。若现有预算确实无法覆盖完整清单，先给出实测瓶颈与局部修补，不直接减少承诺图量或重构整个平台。

### 验证矩阵与完成条件

| 主题 | 必须覆盖的证据 |
| --- | --- |
| 自由组合 | 同功效不同原料可实现；比例改变产生真实强度／产量／副作用差异；不相容组合不能凭名字成功 |
| 品质与难度 | 同方同条件不同操作有质量差异；低阶／同阶／越级难度方向正确；工具和场地变化有效 |
| 五次解锁 | 第4次成功未解锁、第5次解锁；穿插失败不加不清零；一炉多颗只计一次；另一配方不被解锁 |
| 批量 | 越级已熟方在合法条件下量产一般品质；不复制手工精品；缺料／租期／耐久的停止和剩余投入正确 |
| 使用与限制 | 每个药物／器物／符箓有实效；原有战斗行动成本、控制抗性、伤势处置与成长上限继续有效 |
| 特殊成长 | 换名、自创等效变体、赠予和恢复不能绕过效果族次数；满级不能白耗材料或越界升阶 |
| 世界供给 | 节点和尸体取材不复制；NPC与玩家同库存；有限商货先有来源再到店；不刷新唯一物与特殊保护 |
| 信息 | 前端静态目录、选料／排序、报价、叙述和模型输入不直接泄露隐藏属性；必要信息足够作决定 |
| 输入与故障 | 按住松开、键盘自动重复、触屏取消、失焦、Esc、中文输入法、重复收丹、网络未知结果不误判 |
| 完整恢复 | 准备／开工／小游戏暂停／待结算／第5次／批量中断处保存恢复；种子、输入、数量、费用和成功进度一致 |
| 容量 | 目标玩家批次／配方／队列与现有NPC规模同场承载；节点唤醒、长批量和图片加载有实测时间／体积 |
| 美术与正式流程 | 全目录图位有资源引用；选料、采点、租房、三种小游戏和成品使用在真实浏览器可见可操作 |
