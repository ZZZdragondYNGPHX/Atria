# 从玩法想法到实际功能的实施对应

状态：v0.16 实施依赖与交付定义。本文记录已核代码的承载缺口、需要补齐的功能路径和实现次序；不表示新设计已经编译、运行或验收通过。具体机制由各领域模块维护，当前事实以版本化源码与 [Record](../../../records/package/doupo-living-world.md) 为准。

## 本模块的职责

按 [decisions.md](decisions.md) 的实现完整性要求，把玩法中的行为、状态和后果落实到数据、写入、规则、认知、显示与恢复。缺少承载时先补齐实现依赖，保留用户目标；不得把想法仅改成旁白，也不因当前代码没字段而默认删掉目标。

这是执行代理实现每项功能时的必要自查与交付约定，不引入独立审查代理、多轮交叉审查、额外批准或另一套工作流服务。W0–W5按依赖连续推进，具体字段/公式作为实现默认选择校准。

## 一项功能的完整路径

| 环节 | 实现必须回答的问题 | 不足以作为完成证据的情况 |
| --- | --- | --- |
| 状态与身份 | 什么持久事实发生变化，主体/物品/来源引用何处，schema如何表达 | 仅有故事文案、字段名或一个通用标签 |
| 合法写入 | 哪个动作、事件或活动能创建/修改/结束状态，有何前提与代价 | 模型随意给补丁，UI自行改库存或角色状态 |
| 机械后果 | 如何改变可执行能力、效果、时间、资源、风险和后续事件 | 状态写上去了，人物仍照旧做所有事 |
| 决策与所知 | 哪些人能知道哪些变化，AI怎样把它用于选择与改策 | 后台状态对全体公开，或AI完全不读取状态 |
| 投影与操作 | 玩家/模型能读到什么，人物详情如何解释限制，能做什么来应对 | 后端仅私有字段，无实际读口；UI只有漂亮示意图 |
| 保存与历史 | 未完成过程、来源、身体/物品和认知怎样随分支恢复 | 只恢复最终数值，读档后丢限制、重复结算或串入未来 |
| 对应验证 | 用什么代表性过程证明上述连接，失败和重试怎样处理 | 只验证schema通过、流程不报错或模型会说这段话 |

同一状态在多个系统产生影响时，统一查询其实际能力/效果与原因；避免旅行、战斗、工作、修炼各写互相矛盾的一套限制。派生能力可以按需计算或缓存，但原始身体/物品/活动事实只保留一个权威。

## 已核代码的实际起点

基线为package `914c624c9`（规则交付 `38007d02d`）与be.2对应Atria `a9a914c66`。这里是源码调查，不是本轮新运行验证。

- `tools/schema.mjs:6–9` 的人物只有hp/qi/injury等数值；没有身体部位、具体伤实例、永久缺失、受控状态或新目标模型。
- `source/rules/projection.js:12` 与 `schema.mjs:22` 的玩家screen已有injury；`projection.js:3` 与 `schema.mjs:21` 的NPC观察没有伤势字段。正式前端未集成，不能描述为已有伤势详情界面。
- `engine.js:67–92,217–235,354–363` 的进食、恢复、照护和服药直接使用总伤势。它们不能区分骨折、缺肢和其它损伤，新增部位状态后必须同步改造，不可留下通用减数值就恢复所有功能的旁路。
- inventory目前为item/qty，skills为id/level；不能据此宣称装备实例/穿戴/耐久或具体功法运行效果已经存在。
- `engine.js:20–27` 的同主体/对象/种类个人文字会被后续同键更新；重要因果和未解决动机不能只依靠此种最后一条消息。
- `tools/build.mjs` 明确声明Domain、闭合schema、read grants、computation输出、effects、Information sources/views、Bridge与screen。新增概念必须进入完整声明链，不能只改state或一处JS。

## 按玩法核对的承载缺口

下表中的“需补齐”是进入该能力实现的依赖，不代表要一次设计全套基础设施。字段是概念责任；实际结构、边界和绑定在首个实现切片中编译验证并回写真实契约。

| 玩法与现状 | 必须补齐的状态/写入 | 必须生效的规则和最小反馈 | 详细规则与实现依赖 |
| --- | --- | --- | --- |
| 重伤、骨折、缺肢：只有总injury | 有来源的部位损伤、完整性、功能受限与治疗过程；NPC冲突/事件合法写入 | 移动、持握/穿戴、工作、施技、修炼等读取实际能力；本人详情/合法观察解释限制与恢复 | [身体与伤势](character-condition.md)；先于依赖这些后果的冲突样本 |
| NPC修炼/突破：职业日经验 | 已学/运行功法、修炼进度、准备和占用、突破条件与结果 | 身体/物资/环境影响积累，中断保留；详情显示当前活动、准备缺口和结果 | [成长与后台冲突](npc-progression-conflict.md)；不能只加xp并改plan文字 |
| 功法斗技：id/level及少量玩家分支 | 资格、掌握、运行/使用条件和规则效果；学习与训练合法写入 | 选择与施展读取条件，能力差异实际影响活动和交锋 | 同上及 [成长规则](progression-and-consequences.md)；不把秘籍持有等同学会 |

| NPC互战：只有旧玩家交锋 | 真实参与者、分段活动、已接纳动作与结果/资源变化 | 双方实际能力判定，伤势/损耗进入世界；玩家只读已知经过和可知后果 | 同上；完整玩家战斗按D33后续独立实施 |
| 拘束/俘获/逃离：目前无状态 | 控制者/受控者、位置、有效限制、持续占用与解除条件 | 双方可行动能力变化，不能同时被俘又原地经营；合法视角显示状态和可行应对 | [人物能动性](npc-agency.md)、身体/时间模块；先于绑架长链 |
| 人格/情绪/仇怨：背景和评价有限 | 有来源的人格/价值、情绪对象、未解决事项和动机 | 改变选择并能复评/缓和；NPC私有理由与玩家可见线索分开 | [人物能动性](npc-agency.md)；不由一条好感值代表全部 |
| 长期目标/机会改策：当前plan为文字 | 目标、条件、进度、依赖、暂停活动与实际投入 | 完成/受阻/新消息触发改策，多目的部分成功；显示本人活动及已知承诺 | 同上；人物自己的阶段/活动不复用玩家四步队列冒充 |

| 家庭/出生/人口：已有基础 | 新身体/技能/目标/图谱的初始化与来源，边界内接纳和预留 | 新生/成年/照护的能力与身份相符；本人可知家庭数据，不全知人口 | 世界调度/家庭模块；现有样本不自动证明新增数据恢复 |

## 以用户伤势例子贯穿实现

“A使B重伤并损坏手脚”需要先明确发生的是骨折、暂时失能还是肢体缺失；具体区别见身体模块。不同后果可以共存，但不能只写入injury=90再由不同地方任意解释。

实现切片至少贯通：

1. 角色初始化具有可表达的身体与伤记录；NPC冲突的合法结果创建具体伤势及来源，而非旁白先宣布。
2. 人物能力统一推导，当前装备/动作/旅行/工作/修炼重检。例如需要相关肢体能力的动作不可用，活动中已发生部分保留。
3. B及实际观察者获得各自能知道的结果。B可据此求助/休养/改策，A只按自己观察到的情况决定后续，不读取完整私有诊断。
4. 正式读取投影能提供本人伤处/功能限制/治疗状态、相关不可行动原因，NPC只显示已观察或获知的表现；前端把它落实到可打开的人物/伤势详情。
5. 治疗产生有条件的实际变化，永久缺失不被通用减injury或普通回血自动修复；解除限制或仍然受限都要有原因。
6. 途中/治疗中保存，继续变化，再恢复并推进，身体、能力、装备、活动、所知和详情回到同一历史分支。

后端可先用真实读取和本地最小验证入口证明状态/能力/投影路径；角色详情正式接线由既有FE/集成分工完成。没有画完正式界面不妨碍后端实现，但该玩家功能在接线前只能标“后端已实现、界面待集成”，不能宣称整项可玩。

## 构建与宿主预算也是承载条件

新增能力需要同步核对以下真实作者入口，不另造通用服务来回避现有契约：

- state初始值、新角色默认值/准入输出、Domain记录schema和允许命令。
- read grants字段/集合/数量、invariant所需的最小授权输入、computation输出schema与有界effects。
- Information sources/views及主体scope、NPC判断使用的字段、玩家与叙事的合法投影。
- screen/detail读取schema、Bridge绑定/输入/错误、实际前端消费者、保存/恢复及历史引用。

be.2代码中的8人物/8信息/4评价输出、有界集合和公开观察预算均影响扩展；a9已有CPU/输入/schema预算。不能把所有新状态无限嵌入每个人和每次公开screen，也不能先提高全局限额掩盖结构问题。

先用有代表性的身体、器物和个人关系数据验证闭合schema、包构建/安装、真实授权读取/写入与恢复。必要时用有界记录集合、按需详情和稀疏引用减少冗余；具体选择以编译/真实宿主样本为依据，不在本文件宣布某一结构已经通过。

涉及容量的记录要分别统计活跃状态、历史来源、投影、序列化和扫描成本；接口只返回某人的少量记录并不证明没有全域扫描。命中限制后说明具体瓶颈和修正结果，不换Domain、删除活跃证据或复用死者ID来隐藏增长。

## 状态、表达与生成的联系

能力目录与接纳路径定义规则可以产生哪些实际效果。NPC规划和自然语言解析只能提出可执行候选；前提不足时返回可理解的拒绝或缺口，不创建一条已经成功的文本结果。

关键事实如伤处/缺失、物品转移、控制关系和生死应有基于规则结果的稳定表达；模型只使用获准事实展开人物表达。未经实现或未被本次规则结果产生的“断肢”“装备损毁”“家属被扣留”等不能作为系统事实发布。

模型生成错误时修正或重试表达、采用已有事实的受控表达，不按错误文字反向补写世界，也不重做已提交扣费或攻击。自由文本一致性与规则正确性分别验证，不能声称仅靠提示词永不误述。

## 实施顺序与完成状态

W0先形成少量关键状态/作用/读取的实际实现；W1接合法动作与能力限制，再让W2–W4的经济、主动社会和长链使用它们。每完成一段即更新真实契约与Record，避免先铺满所有剧情然后发现底层无法表达。详细阶段仍只有 [制作稿](production-plan.md#实施顺序与完成依据) 一份权威。

代表性切片至少覆盖身体损伤与活动限制、装备状态与损耗、受控/释放、关系认知与消息、生产/到货，各自含合法写入、受影响动作、按视角读取及恢复。测试只用于直接相关必要验证，代码/fixture按治理仅本地保留，不额外安排独立审查。

| 实际进展 | 可以报告的完成程度 |
| --- | --- |
| 只有文档/概念字段 | 设计完成，待实现 |
| 有代码但未通过真实声明/构建/运行 | 实现中，不宣称可用 |
| 状态/规则/读口及恢复有实际证据 | 后端对应能力已实现，注明样本与边界 |
| 已有真实界面读取/操作/限制反馈 | 该玩家功能已接线，注明尚欠的玩法或视觉 |
| 目标场景含失败/中断/恢复贯通 | 对应范围完成，保留实际容量与未覆盖部分 |

并非每个对象都需要独立页面：人物详情、行囊、活动/关系详情等可复用入口。但每个影响玩家理解和决策的状态，都要有合法可读且可理解的表达。完整玩家战斗按D33仍在后续范围；身体和世界后果不因此只留文字。
