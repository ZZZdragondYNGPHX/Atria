# 《雾灯旅舍》外部前端设计需求包

版本：v0.9 / 2026-10-15。用途：把已确定的游戏方向转成精致且可延展的前端设计。这个包独立可读，不需要访问代码仓库或其他对话。

## 1. 怎样交给设计 AI

将本文件与下面两份文件一起发送，复制 §2 的任务说明作为消息：

1. [design-brief.md](design-brief.md)：公开背景、体验目标、媒体意图、规则摘要和可直接使用的示例文案。
2. [interface-requirements.md](interface-requirements.md)：完整界面/操作/状态清单及覆盖矩阵。

请只发送这个三文件需求包。完整作者企划含谜底与后期情节，不是外部视觉设计所必需；本包已提供足够的安全内容。文件之间有冲突时请明确指出，保持已确定的游戏目标，提出具体解决建议。

## 2. 可直接发送的任务说明

> 请根据附件为原创游戏《雾灯旅舍》做前端设计。你负责把审美与交互打磨好，拥有构图、排版、配色、字体、材质、组件和动效语言的设计空间。
>
> 游戏是一部温暖、克制、带轻悬疑的旧式海岛群像冒险。玩家在风暴前的三天临时代管旅舍，与几个陌生人互相照应。世界里有少量真实但不明说的超自然；有些遗憾无法弥补，最后仍留下温暖和希望。图片主要在制作期由生图接口产出，游玩按剧情切换；音效以随包环境声和事件短音为主。
>
> 请先读完这三份输入，在这个具体世界里形成自己的设计观点。重点表现“一个能停留、能阅读、也能做事的海岛旅舍”。请自行决定合适的视觉结构，不必照搬通用聊天界面或后台面板。
>
> 必须交付三个文件：`foglight-inn-concept.html`、`feature-presentation.md`、`frontend-guidelines.md`。HTML 只需把少量代表画面和交互做到精致，不要求实现全部功能。功能表现说明必须覆盖清单中每个 S/A/ST 标识，解释 HTML 没画出的功能如何呈现。整体指导要让后续实施者可以一致地完成所有其他界面。
>
> 请用需求包中的真实中文样例和固定数据，精修主游戏、记事/人物信息、行动预览与结果三个代表场景，并展示窄屏适配。至少能操作一次“发起 → 预览 → 取消或确认 → 结果”的模拟流程，另能查看等待、不可用和失败状态。演示数据是本地模拟，不接入模型、账户或生图服务。
>
> 请交付能直接打开的单 HTML，内嵌必要 CSS/JS，避免要求安装构建环境。两份文档使用 Markdown。若认为需求需要调整，请保留原标识并写清建议；不要默默删功能或增加新的玩法体系。

## 3. 三个输出文件的职责

### 3.1 `foglight-inn-concept.html`

它是可操作的审美标杆，允许局部完整；不承担完整游戏实现。请达到这些要求：

- 主游戏、信息层、行动预览/反馈三个代表情境有足够细节，能够判断阅读、人物、场景、数字和操作之间的关系。
- 真实交互包括打开/关闭信息、选择一个行动、修改或取消预览、确认并看到固定结果；设置或演示入口可切换忙碌/不可用/失败/窄屏示意。演示工具明确标记，不伪装成正式玩家功能。
- 适配约 1440×900 的桌面与 390×844 的窄屏，允许设计自己的断点；缩放/大字时核心内容和返回可达。
- 字体、配色、空间层级与图像比例体现旧式海岛的生活感；长时间阅读舒服。温暖来自光、材料、尺度与人物，不只给通用模板换一层米色。
- 示例场景图/人物图可用少量原创生成样图、原创内嵌图形或许可清楚的素材来确立构图。说明来源和替换要求；关键画面不可只留大块无内容灰框。样图不要求是最终发行资产。
- 单文件内嵌 CSS/JS；样图可内嵌。字体提供可靠本地回退。核心布局和交互不依赖远程 CDN、在线接口、账户或构建环境。
- 音频演示遵守首次手势，可没有实际录音但必须清楚表现启用/静音/音量状态；如添加样音说明来源并标为示意。
- 通过键盘可操作代表流程，焦点可见且恢复正确；触控入口不依赖 hover；尊重减少动态效果。
- 模拟与正式状态分开，页面中说明“交互与数据为设计示意”。不要把内部需求 ID、数据结构或技术诊断当作玩家主画面内容。

如果你的环境能运行浏览器，请实际查看桌面与窄屏截图并操作代表流程后修正。

### 3.2 `feature-presentation.md`

这份文档解释完整前端如何工作，必须包含：

1. **信息架构与主要流程**：界面职责如何组合、玩家怎样进入与返回、桌面与窄屏的对应关系。
2. **逐界面说明**：覆盖 S01—S13，描述主要信息、层级、入口、适用状态；可附简图。
3. **逐操作映射表**：覆盖 A01—A37；列原 ID、玩家可见名称、入口、条件、预览/确认、成功/失败反馈、返回和焦点。可合并视觉控件，不能丢掉语义。
4. **逐状态说明**：覆盖 ST01—ST16；
5. **媒体与内容**：图片切换/裁切、人物与正文、事实/说法/推测、声音控制与文本替代如何协同。
7. **差异与建议**：合并、重命名、新增建议、已知取舍、需要产品配套的音频能力，不把建议伪写成既有实现。

这是呈现与交互说明，数值和玩法使用输入基线；不要求设计者发明后端协议或另写游戏规则。

### 3.3 `frontend-guidelines.md`

这是跨界面复用的整体设计指导，必须能指导 HTML 未画的页面，至少包括：

- **设计观点**：一句明确的视觉命题，解释为何适合这个海岛、这段共同生活与轻悬疑。
- **颜色与排版**：可执行的命名色值/语义色、字体角色、中文字体与回退、字号/字重/行距、阅读宽度与数字排版。
- **空间与层级**：间距、密度、对齐、边界、表面/遮罩、层级和响应式规则；给出适用情境，避免所有内容一个样式。
- **组件与状态**：按钮、输入、选择、人物条目、资源、记事、通知、预览、确认、错误/空态与导航的统一规则；普通、hover、focus、pressed、disabled、busy 的差异。
- **图片和文字**：场景/人物/物件的画幅、构图与裁切安全区、遮罩与对比、正文承载方式、字体与插画的关系；示意与最终资产的替换要求。
- **动效与声音**：交互反馈的用途和时长/曲线建议，场景与信息切换，减少动态效果、声音启用/静音与阅读协调。
- **无障碍与设备适配**：文字可读、非颜色单一提示、焦点顺序与返回、触控区域、窄屏输入法、大字、长内容和无鼠标操作。
- **实施说明**：哪些规则必须保持、哪些允许在 Atria 能力内调整、参考图/代码对应位置，以及作者最容易误解的地方。

逐项操作细则归上一份文档，本文件集中统一设计语言。可以提供 CSS 变量表或简短组件片段帮助准确复现。

## 4. 交付前自查

- 三文件名称清楚，HTML 可直接打开，文档内容完整，没有伪造附件地址。
- 代表情境足够精致，适合游戏世界；画面与装饰不挤占阅读和操作。
- 每个 S/A/ST 均有对应设计，M01—M07 能找到说明；局部 HTML 的范围有明确标注。
- 中文示例和数字可读，动作名称一致，角色说法与事实分开，没有提前揭示谜底。
- 预览不先扣账，确认只产生一次固定示意结果，取消/等待/失败/返回有区别；窄屏和键盘流程能理解。
- 设计三文件之间一致；

请最后用几句话解释你的设计选择，并列出相对需求包的任何实质变化。我们会据此审阅与修订正式企划，之后才进入游戏实现。
