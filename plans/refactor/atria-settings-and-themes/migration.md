# Atria 设置与主题 — 升级与导入迁移

- 状态：已实施；真实实现与验证见 [Record](../../../records/refactor/atria-settings-and-themes.md)。
- 本文件定义首次升级、旧资产保留、主题转换及导入行为权威。
- 日夜槽、颜色角色、主题 CSS 及预览规则归 [themes.md](themes.md)。
- 页面组织与控件归属归 [settings-ui.md](settings-ui.md)。
- 事实盘点与资料见 [audit-and-research.md](audit-and-research.md)。
- 验收见 [validation.md](validation.md)，执行规则归 [Governance](../../../README.md)。

## 1. 迁移目标

已有用户升级时保留当前可见外观、现有个人偏好和主题原件。
新主题能力应明确启用，不从旧默认值猜测用户新的明暗意图。
旧文件兼容不意味着重新启用旧聊天布局或已经退出默认产品的控件。
转换过程需要可解释、可恢复，并沿既有数据权威完成。

当前默认界面为固定 Serene Canvas 浅色。
旧 power_user.theme 与 SmartTheme 值仍可能描述暗主题。
旧根变量被浅色桥接遮住时，不能将它们当成当前实际可见深色。
旧默认 theme=Dark Lite 也不能证明用户主动选择过深色。
这些是迁移判断的输入事实，实际证据入口归审计模块。

## 2. 用户分类及首次默认

新旧用户分类应基于账户与迁移状态的可靠证据。
不能因为用户选择名为 Dark Lite 就判定为主动深色用户。
也不能因浏览器本地状态丢失就将已有账户重新当成新用户。
迁移完成后要能识别已处理状态，避免再次覆盖后续选择。

| 用户 | 初始模式 | 日间槽 | 夜间槽 |
| --- | --- | --- | --- |
| 新用户 | 跟随系统 | Serene Canvas | Dark Lite |
| 已有用户 | 浅色 | 保留当前 Serene Canvas 基线及有效 CSS 的适配结果 | 优先旧选择的适配结果，否则 Dark Lite |

已有用户的夜间槽预选不自动启用深色。
只有用户明确选择深色或跟随系统后，夜间槽才按正常规则生效。
系统当前为深色也不能在首次迁移时替已有用户改为 system。
新用户则按当时系统偏好解析，不人为强制首次浅色。

首次升级以简短提示解释当前外观已保留、深色主题已准备好。
提供查看外观设置的入口，不强制进入迁移向导。
提示展示不能成为主题资产转换与偏好保留的前置审批。

## 3. 旧用户当前外观

保留当前浅色基线与已生效 CSS 共同形成的实际外观。
不要用被固定浅色遮住的旧 tint 将日间主题直接重建成深色。
当前 CSS 中的用户修改可能改变局部或全局观感，应保留原文和启用状态。
即使它已将实际界面改为深色，也不因迁移初始模式为 light 而主动关闭或覆盖有效 CSS。
新增设置结构可能使旧选择器失效，不能承诺所有 CSS 效果逐像素恢复。

当当前 CSS 或用户修改不能由只读 Serene Canvas 原件承载时，
为迁移结果创建可识别的自定义副本，将现有 CSS 附着在该副本。
此副本承载用户当前外观，不修改内置主题。
副本的具体标识、去重与事务组织由实施决定。

迁移不增加全局 CSS 覆盖层。
同一份当前生效 CSS 不得同时从旧注入器与新主题注入器生效。
不能先复制进新主题，又继续作为另一份个人覆盖重复应用。
切换至新主题体系后的唯一 CSS 来源按主题契约执行。

当前已生效 CSS 的保留规则不同于新导入旧主题的默认关闭规则。
前者维持升级前状态，后者避免导入资产时未经预览立即改变界面。
二者不得因为共用转换器而混用默认值。

## 4. 夜间槽及同名修改

优先为夜间槽准备用户原先选择的旧深色主题适配结果。
若用户实际主题与内置同名原件不同，以用户资产内容为输入。
名称相同不意味着可以用新版内置配色覆盖用户内容。
找不到旧选择、内容无法有效转换或归属不适合时，夜间槽降级为 Dark Lite。
降级需要保留原选择与原文，不删除不可用资产。

内置 5 个旧主题的名称与配色意图继续保留。
新版内置资产只作为产品只读主题，不覆盖用户已经修改的同名文档。
用户变更内容转换为自定义副本，避免与产品原件混为同一身份。
界面需能区分内置、自定义及迁移副本，不能仅靠重名判断归属。

未保存进某个主题的当前颜色值仍是用户现有数据。
不能只转换磁盘主题文件而漏掉当前设置中的颜色修改。
这些值应完整保留为可恢复信息。
它们不反向决定首次日间显示，也不擅自覆盖原已选主题资产。

## 5. 原件、偏好与兼容数据

至少保留以下迁移输入的完整内容：

- 用户当前相关设置及尚未写入主题文件的颜色调整。
- 用户现有主题文档，包括同名但被修改的内容。
- 原 Custom CSS 文本与当前启用状态。
- 旧主题中的布局、行为及未映射字段。
- 转换时无法解释、但需要保留的原始信息。

原始信息不能只留在日志或暂存缓存中。
用户应能取回完整原始主题文件，导出或恢复时不依赖重新猜测。
原文保留与新主题的有效字段要有清楚边界，避免兼容字段再次生效。

个人字号、输入方式、滚动、语言和减动等继续沿现有偏好权威保存。
主题迁移、切换和导入不得用主题内旧偏好覆盖它们。
旧聊天布局、头像表现、计时等遗留主题字段仅作兼容数据。
不为保留这些字段重新添加默认设置控件或旧聊天外观。

## 6. 导入的共同流程

主题导入首先创建资产候选，不自动应用到当前外观或日夜槽。
先识别格式并校验，再展示结果、命名与保存反馈。
任何转换预览都沿主题契约的临时覆盖规则执行。
导入成功与应用成功是两个不同结果，界面应分别表达。

名称冲突统一采用另存。
可以建议可理解的新名称，不默认覆盖用户同名主题。
内置主题不可由导入覆盖。
取消导入或校验失败时，不留下部分主题、半更新槽位或已应用 CSS。
保存失败需保留可重试输入，不显示成功提示。

不得静默删掉未知字段后声称完整导入成功。
对不支持的数据，需要明确拒绝或按下述旧格式规则完整保留。
格式判断不能仅由文件名、主题名称或是否存在某个旧颜色字段决定。

## 7. 原生格式校验

原生主题应有可识别的版本与明确的结构。
最小信息范围由主题契约规定；字段命名属于实施细节。
按支持版本的字段、类型、明暗属性、颜色值和 CSS 结构校验。
非法颜色、坏类型、缺少必要信息或不支持的版本要给出可操作错误。

未知新版格式应拒绝，不将其降级成旧主题后丢掉新字段。
已识别原生版本出现不支持的字段时，也不能静默忽略后另存。
错误应定位到可理解的字段或原因，而非只显示笼统的解析失败。
允许扩展的边界如需存在，应在支持的格式合同中明确，不能临时猜测。

校验和转换完成前，不执行资产写入与选择更新。
批次或单文件中的失败不得造成当前主题部分生效。
原生格式的安全降级不能等同于把坏值写成默认值并悄悄保存。
是否能补全的角色需要由该版本合同明确。

## 8. 旧格式转换

旧主题已识别字段中的有效配色映射为原生颜色角色。
缺失的原生角色从确定的基础主题补齐，并标明属于适配结果。
补齐不依赖用户当前正在看的页面或另一主题的残留值。
不将旧透明 tint 原样套进所有新表面，需保证可读性与角色一致性。

旧主题中的行为、字号、减动和布局字段只保存为兼容数据。
未映射或未知的旧字段连同完整原文保留，不执行其旧行为。
结果说明区分已适配配色、已补全角色与仅保留数据。
旧名称的保留不构成旧 DOM 布局或任意 CSS 的还原保证。

新导入旧主题附带 CSS 默认关闭。
保留文本；用户可以在预览中打开检查后，随该主题确认保存。
导入动作本身不注入 CSS，也不为方便兼容新增全局覆盖。
该规则不影响第 3 节对升级前已生效 CSS 的保留。

## 9. 保存与重复执行

继续复用 NamedDocRepo、既有主题 API 与用户设置持久层。
不得用本地临时缓存作为主题资产或迁移完成的唯一权威。
具体如何扩展现有文档结构和接口在实施中决定。
不为适配格式新增另一套主题库或跨平台 token 编译系统。

重复进入设置、刷新和重复检查迁移状态不能生成无限副本。
已迁移后用户的主题、CSS 和模式选择不能再次被首次默认覆盖。
资产写入、用户选择与迁移标记之间要有可恢复的失败顺序。
失败结果应说明哪些已保存、哪些未完成，避免模糊的全量成功状态。
已发出写入的取消、部分保存与定向重试，复用 [主题保存合同](themes.md#8-浏览编辑及离开保护)。

原件保留不能依赖对内置主题的破坏性改写。
出现版本或命名冲突时应保护现存资产，提供明确修复结果。
迁移完成的判定需要真实读取与恢复证据，不以写入动作未报错代替。

## 10. 实施验证路由

现有代码与执行基线在开始实施时重新核对，实际 Git 状态优先。
审计模块记录现状证据，本文件只定义目标迁移规则。
需要覆盖新旧用户、同名修改、当前未保存颜色、有效 CSS 与未知字段。
同时验证首次显示、日夜预选、失败恢复和重复执行后的资产完整性。

预览、确认、取消、系统变化和草稿保护的详细语义归主题模块。
具体场景与证据归 [validation.md](validation.md)。
本方案不新增审批、阶段自动停工或 API 配额。
