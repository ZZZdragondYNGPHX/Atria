# Atria MCP 当前主线适配 — 已确认决策

本文件只保存本任务已确认、影响多个模块的决定。当前确认日期为 2026-10-20，来源为本任务三轮讨论后的用户明确回复。

## D1 — 完整适配当前主线

- **决定**：覆盖失效接口修复、业务语义纠正和当前主线新增工作流；逐域核实已有、部分、缺失和不应暴露的能力。
- **理由**：局部修补无法解决旧 Orchestrator 被替代、Runtime 审批入口退役及 Storage 生命周期变化。
- **影响模块**：全部。

## D2 — 版本目标只面向当前 main

- **决定**：允许退役旧 action、字段和浏览器桥接，不为旧版 Atria 建立兼容层。实施时以复核后的主线源码和原生契约为准。
- **理由**：产品处于开发阶段，应复用当前唯一业务权威，避免双轨实现。
- **影响模块**：全部，尤其编排、Runtime 和 Skills。

## D3 — 允许必要的产品侧小改动

- **决定**：主要实现留在 `plugin`。正规原生接口存在确切缺口时，可在产品源码任务工作空间补充必要接口，并说明所属权威与调用场景。
- **理由**：例如独立作者图像目前缺少受控二进制读取入口，仅修改 MCP schema 无法完成工作流。
- **影响模块**：编排与审批、媒体及其他经核实需要产品接口的领域。

## D4 — 沿原生 V3 与原始业务入口接入

- **决定**：按 [V3 模块](orchestration-approval.md) 对接服务端 Plan / Binding / Run / Effect 和各域正式入口；外部 AI 直接创作与用户显式委托内置模型分开；按产品实际能力保留 V3 formal_commit 和直接 Studio / Task 两类明确工作流。
- **理由**：复用主线业务权威并保持当前支持范围；V3 请求不会因原生审批失败而切换到直接提交。
- **影响模块**：V3、Studio / Project、Session / Runtime 和所有执行状态关联。

## D5 — 分层授权，以原生实际审批要求为准

- **决定**：MCP 客户端授权、技术预检 / reviewHash、模型 review 与原生真人 Review 各保留原职责；原生真人审批按 authority 的 `requiresApproval` 执行，详细合同归 [V3 模块](orchestration-approval.md)。
- **理由**：确保当前产品要求的真人审批，同时避免把每个图节点或技术摘要都当成人工审批。
- **影响模块**：全部领域的风险分类、预检、执行和正式发布。

## D6 — 采用 A：原生批准后自动续接一次精确派发

- **决定**：一次 MCP 授权覆盖明确披露的固定业务准备与最终派发；原生批准后，在原实例、有效期限和未变化的精确业务绑定内自动继续一次。过期、重启或前置变化按 [V3 模块](orchestration-approval.md) 重新核验和授权。
- **理由**：保留原生真人审批，减少同一已批准操作上的重复确认。
- **影响模块**：MCP 执行器、调度、Operation Journal、V3 提交工作流与恢复。

## D7 — 剩余领域范围按第三轮收口

- **决定**：接受 [领域与验收模块](domains-acceptance.md) 的全领域范围、主线实际能力边界及必要产品小接口，按 [index](index.md) 的依赖顺序实施。具体 API shape 沿已确认职责核实，不将原生尚无权威的执行或运维能力纳入本次默认扩展。
- **理由**：补齐现有正式能力的完整工作流，同时避免把适配任务扩为新产品能力开发。
- **影响模块**：全部领域、产品侧小接口与实施安排。

## D8 — 验收采用第三轮推荐基线

**状态：旧的固定推荐基线已撤销。** 实际完成历史见 Record；后续改动的检查只按 [Governance §12.2](../../../README.md#122-minimal-validation-and-runtime-checks) 选择，不重开全领域、双 Backend、真实模型和多客户端验收。产品权限与审批合同不变。
